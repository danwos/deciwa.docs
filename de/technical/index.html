Technischer Überblick¶

Status: Entwurf

Wie die nächste Version (0.1) gebaut wird – für jede Version aktualisiert. Vorschläge von Claude, 2026-10-19; nichts auf diesen Seiten ist verbindlich, bis Daniel es freigibt. Fragen, die die Arbeit blockieren, sind in Offene Fragen gesammelt.

Ziel¶

Release 0.1 bauen (Roadmap): die CLI mit dem offenen Dateiformat, die Adapter für Markdown, rST/Sphinx-Needs und reinen Text sowie die Agent-Skills deciwa-work und deciwa-ask – gut genug, dass Daniel deciwa in seiner Wissensbasis statt [CHECK]-Markierungen nutzt.

Nicht in 0.1: push / pull, VS Code, Chrome, monsterbrain, gehosteter Dienst, Python-/HTML-Adapter, die eigenständige Engine. Das Design darf sie aber nicht blockieren – vor allem nicht das Review am Ergebnis (Reviews finden auf den Erge... (DEC_REVIEW_ON_RESULTS)) und Host-Apps (Host-Apps und die eigenständige Engine).

Architektur¶

Jedes Frontend – die Integrationen wie auch die Agent-Skills – spricht mit der deciwa-CLI und ihrer Core-Bibliothek, nie direkt mit den Dateien (Die CLI ist der Master, mit... (DEC_CLI_MASTER)). Die CLI speichert Reviews in .deciwa/ im Repository oder später im gehosteten Dienst.

Repository¶

deciwa/
├── packages/            one package per part – see below
│   ├── core/            deciwa-core     model, .deciwa/ store, engine
│   ├── server/          deciwa-server   review server
│   ├── cli/             deciwa-cli      the deciwa command
│   ├── ui/              deciwa-ui       review overlay (JS/CSS)
│   ├── sphinx/          deciwa-sphinx   Sphinx extension
│   ├── client/          @danwos/deciwa-client   engine client for host apps (TypeScript)
│   └── monsterbrain/    deciwa-monsterbrain     the monsterbrain extension
├── docs/                these docs – product, integrations, decisions,
│                        technical details
├── .deciwa/             review data of these docs (config.toml: what must be approved)
├── mockups/             first clickable mock-up of the feedback UI, demo recorder
├── pyproject.toml       the uv workspace (all packages + docs tools)
└── uv.lock

Pakete¶

Die Aufteilung in Pakete ist deciwa ist ein Repository a... (DEC_PACKAGES).

deciwa ist ein Repository mit einem Paket pro Teil – ein uv-Workspace. Alle Pakete teilen sich den Python-Namespace deciwa.

deciwa-sphinx importiert deciwa-server nicht: ein statischer (Offline-)Build braucht keinen Server. Mit deciwa serve führt der Server den Sphinx-Build aus, und die Review-Oberfläche in den Seiten spricht mit der JSON-API des Servers.

Regeln:

  • Logik lebt nur in deciwa-core. Die Offline-Engine in deciwa-ui spiegelt ihre Regeln für Reviews ohne Server und muss mit ihr Schritt halten.

  • deciwa-server und deciwa-cli werden von jeder Integration wiederverwendet, die im Browser reviewt oder die CLI aufruft.

  • Ein Integrationspaket hängt von deciwa-core und, für eine Browser-Oberfläche, von deciwa-ui ab – nie von einer anderen Integration.

Einrichten¶

$ uv sync                          # all packages, editable, plus the docs tools
$ .venv/bin/deciwa serve           # the CLI from packages/cli

deciwa in einem anderen Sphinx-Projekt nutzen:

$ cd ~/workspace/deciwa/packages
$ uv pip install --python <project>/.venv/bin/python -e core -e server -e cli -e ui -e sphinx
