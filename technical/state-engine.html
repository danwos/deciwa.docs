State engine¶

Status: draft

Proposals by Claude – not binding until Daniel approves them.

State is never stored, always computed from the annotations plus the current source. The engine does it in three steps for every annotated file.

1 · Resolve¶

Proposal: Selectors are tried in a fixed order and the first unique hit wins PROP_RESOLVE
status: draft
refines: DEC_NO_MARKERS, PROP_SELECTORS
refined by: PROP_FINGERPRINT

  1. Structural – the adapter’s element list has an element with exactly this selector.

  2. Text quote – the exact text occurs once in the file; if it occurs several times, prefix and suffix decide. Whitespace differences are ignored.

  3. Position – only if the text at that position still matches the fingerprint.

If the selector that hit is not the first one, the engine reports a relinked hint so deciwa can update the stored selectors (only on an explicit deciwa relink, never silently). Nothing hits → orphaned. Text quote and position follow the W3C Web Annotation Data Model.

Moved elements¶

A counter in a selector – an array index (json:/steps/2), the paragraph number in md:paragraph:Setup#2 – moves when something is inserted or removed in front. The element under the old selector then has a new fingerprint, although the reviewed element is unchanged one place further down. So when the element found by its selector changed and the annotation has no text quote, the engine looks for elements of the same kind whose selector differs only in its numbers and whose text is still the reviewed one. If there is exactly one, the annotation follows it and keeps its state; otherwise the element under the selector counts, and it is stale. The selector is a hint, the reviewed text decides (JSON and YAML files are rev... (DEC_DATA_ADAPTERS)). This works for every format.

2 · Compare¶

Proposal: The fingerprint covers the source text with whitespace normalised PROP_FINGERPRINT
status: draft
refines: PROP_RESOLVE
refined by: Q_FINGERPRINT_MARKUP

sha256 over the element’s source text after Unicode NFC, trimming and collapsing runs of whitespace into one space. Markup stays in: turning a word bold makes an approval stale.
Question: Should pure formatting changes make an approval stale? Q_FINGERPRINT_MARKUP
status: open
to: Daniel
refines: PROP_FINGERPRINT

With markup in the fingerprint, bold, a new link or a re-wrapped table makes an approved statement stale. Without it, only changes to the words do – but deciwa then has to strip markup per format. Proposal: keep markup in for 0.1 (simple, safe); revisit if it is too noisy in the knowledge base.

3 · State¶

Ratings and notes never change the state. For everything else the engine looks at the open and the latest annotations of an element and picks the first rule that applies:

State

1

target not found

2

3

latest freeze is in force

frozen

4

5

6

7

approved

8

9

unreviewed
Proposal: State rules in this order PROP_STATE_RULES
status: draft
refines: DEC_DECISION_IS_APPROVAL, DEC_FREEZE, DEC_THREE_MODES
refined by: Q_UNFREEZE

An open request is shown as a badge on top of every other state, so approved with an open question is still visible as approved. A resolved quick action does not approve anything: after deciwa resolve the element falls back to its previous state, and the stale check shows that it was changed.
