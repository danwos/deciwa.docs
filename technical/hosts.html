Host apps and the standalone engine¶

Status: hosts decided, standalone engine draft

The engine server, the host element source and the client are decided (2026-10-22) and built; monsterbrain is the first host (monsterbrain is the first h... (DEC_HOST_ORDER)). The standalone engine further down is still a proposal.

A host is an app that renders content itself and shows deciwa inside it: monsterbrain first, then VS Code. Two decisions frame this page:

  • Host apps get deciwa as an ... (DEC_HOST_EXTENSIONS) – the host only offers generic extension points; everything deciwa-specific is an extension in this repository.

  • The Python parts can be shi... (DEC_STANDALONE_ENGINE) – the Python parts ship as a standalone binary, so a host works without Python on the machine.

Engine as a server for a host¶

A host talks to deciwa serv... (DEC_SERVE_API_ONLY)

$ deciwa serve --api-only --root <folder> --port 0
{"deciwa": "0.0.1", "api": 1, "port": 41873, "token": "…", "root": "/home/daniel/brain"}

  • Handshake: the first line on stdout. root is the folder that holds .deciwa/ – it may lie above the folder the host opened; the host maps its paths by the difference. Without .deciwa/ the line is {"api": 1, "error": {"code": "no-deciwa", …}} and the engine exits with 2; the host can then offer deciwa init --at <folder>.

  • Token: every request carries the header X-Deciwa-Token; other local pages cannot call the API. --token or DECIWA_TOKEN set it, otherwise it is random.

  • Lifetime: the engine stops when its stdin closes, so it never outlives the host. --keep-running turns this off (for trying it in a terminal).

  • No site: everything outside /api/ answers 404.

Endpoints for hosts, next to the ones of the review server (/api/page, /api/annotate, /api/reply, /api/project, /api/todo, …):

Endpoint

Returns

GET /api/version

app (engine version), api (major of the JSON API), root

GET /api/elements?source=<path>

the elements of a file with selector, kind, label, line, text and fingerprint – from the elements index of a build, else from the adapter for the file type

POST /api/elements {source, title, elements}

keeps the elements of a page the host scanned itself (rendered HTML), like the pages of a website in .deciwa/web-pages.json

GET /api/summary[?sources=a,b]

per file: counts per state, open questions, jobs for the AI, required and done – without sources for every file with review data

GET /api/facts[?sources=a,b]

the facts of facts files ([facts] in the configuration): per file its facts with selector, kind, label, heading path, line, state and group, the state of the whole-file approval (file:) and the counts per group – without sources every facts file

POST /api/approve-facts {sources}

approve every fact of these facts files that is not approved yet, and each file as a whole

GET /api/events

server-sent events {"type": "changed", "sources": […], "review": …, "config": …} when .deciwa/ or a reviewed file changes

Files without a build are read by their adapter on the fly (Adapters), so a plain Markdown folder such as a knowledge base needs no Sphinx: deciwa todo, show and the project overview cover every file with review data and every file under review.paths.

Overlay in a host¶

In a host the overlay gets ... (DEC_HOST_ELEMENTS)

The host marks its rendered view:

  • every block carries data-line="<first source line, 0-based>" – what markdown-it does with its token maps and what the VS Code Markdown preview already does; lines count the frontmatter,

  • the host adapter sets data-deciwa-source="<path relative to the root>" on the container.

hostElements() in packages/ui/js/host.js loads nothing itself: the adapter passes the elements from /api/elements, and each is matched to the block of its kind that starts on its line (heading → h1–h6, paragraph → p, item → li, row → tr, code → pre). Elements of a build index whose lines are not exact (Sphinx) fall back to their text. Blocks without a match are not reviewable.

startOverlay() takes a few options for hosts: api (calls go through the host, not fetch), scroller (the element the content scrolls in; the UI is mounted inside it), keys: "review" (keys only in review mode – the host keeps its own shortcuts), tools: false (no floating pill), openDoc (open another file in the host) and focus. It returns dock() / undock() to put the panel into the host’s side panel, setReview(), focus(), refresh() and destroy(). Tree views also pass reveal(node) (see below).

Line views (source code): the host marks every line with data-line; with hostElements(container, elements, {ranges: true}) the lines from line to end of each element are grouped into one block, nested as the elements are, so methods sit inside their class. unwrapRanges() undoes it.

Tree views (JSON, YAML): the host marks every node of the tree with data-pointer="<JSON Pointer>". Elements that carry a pointer (the data adapters, JSON and YAML files are rev... (DEC_DATA_ADAPTERS)) are matched to the node with the same pointer (pointerElements() in host.js). A tree hides collapsed nodes, so the host passes reveal(node) to startOverlay(): the overlay calls it before it shows or opens an element, and the host opens the collapsed nodes around it. The state bars skip elements that are hidden.

In a diff the overlay runs on the new side only; the old side is read only. Rendered HTML files: the host marks every start tag with data-line; the elements come from the engine’s HTML adapter and are matched by line and tag (HTML files are read by an a... (DEC_HTML_ADAPTER)). Only a page the adapter cannot read falls back to the DOM scan of the web script, whose elements go to the engine with POST /api/elements.

The monsterbrain extension¶

packages/monsterbrain maps monsterbrain’s extension interface v0 (docs/extensions.md in the monsterbrain repository) to client and overlay:

monsterbrain extension point

deciwa uses it for

background process (onRoot, deactivate)

start the engine for the open folder, stop it with the app

calls and events

the window’s API calls go through the main process (the token stays there); change events refresh overlays and marks

view injection (mountView)

overlay on rendered Markdown (mode: "rendered"), on code views (mode: "lines", line ranges) and on the tree of JSON and YAML files (mode: "tree", nodes by data-pointer, reveal(node) opens collapsed nodes) – not on the old side of a diff

frame scripts

overlay in rendered HTML pages; monsterbrain marks start tags with data-line; calls from pages reach only reading and feedback

panel section

the deciwa panel of the file, docked (dock()), or Set up review for a folder without .deciwa/

toolbar

the switch Review on/off next to View · Source · Diff

decorations

marks in tree and change view from /api/summary: 2? questions, a number for jobs, 1! stale, 3/5 required, ✓

commands

Shift R (review mode); the overlay’s keys listed in monsterbrain’s help

children of side bar views

the facts view: the facts of every file from /api/facts, a click selects the fact in review mode, the action Approve all facts (Shift A)

MCP tools

deciwa_feedback, deciwa_show

Views opened while the engine is still starting attach as soon as it is ready. Review mode is one setting for all files: the overlay keeps it, and rendered HTML pages follow it.

Client¶

One TypeScript client for a... (DEC_CLIENT_PACKAGE)

packages/client (@danwos/deciwa-client) runs in Node – the host’s main or extension process, never in a page, so the token stays there:

  • findEngine() – the path from the host’s settings, the engines bundled with the host, then deciwa on PATH,

  • new Engine({root, enginePath, bundled}).start() – starts serve --api-only, reads the handshake, refuses another API major (api-mismatch), restarts after a crash (at most three times a minute),

  • typed calls (elements, page, summary, todo, annotate, hostPage, call for any endpoint) and events() with reconnect,

  • initFolder() – deciwa init --at <folder>.

npm test in packages/client starts the engine of the checkout against a temporary folder.

Standalone engine¶

Proposal: The engine is built with PyInstaller, one folder per platform PROP_ENGINE_BINARY
status: draft
refines: DEC_STANDALONE_ENGINE, PROP_PYTHON_CORE
refined by: PROP_VSCODE_PLATFORM
answered by: Q_ENGINE_BINARY_TOOL

  • Content: deciwa-core, -server, -cli and the overlay files of deciwa-ui. Not deciwa-sphinx: Sphinx builds keep running in the docs project’s own Python environment.

  • Form: PyInstaller one-folder (starts fast; one-file unpacks on every start), so the host can sign every file inside.

  • Platforms: linux-x64, linux-arm64, macos-arm64, macos-x64, windows-x64 – built in GitHub Actions on each platform, smoke-tested with deciwa --version and serve --api-only against a test folder.

  • Release: a zip per platform in the releases of danwos/deciwa. A host pins an engine version and fetches it at its own build time; it never downloads code at run time.

  • Signing: the host signs the bundled engine together with its own code (Apple notarisation requires every binary inside the app to be signed).

  • Size: expected 20–40 MB per platform; to be measured with the first build.
Proposal: VS Code ships one package per platform with the engine inside PROP_VSCODE_PLATFORM
status: draft
refines: PROP_ENGINE_BINARY

vsce package --target <platform> builds one extension package per platform, each with its engine. A universal package without engine uses deciwa on PATH – for platforms without a build.
Question: Which tool builds the standalone engine? Q_ENGINE_BINARY_TOOL
status: open
to: Daniel
answers: PROP_ENGINE_BINARY

Proposal: PyInstaller – widely used, simple, no C compiler. Alternatives: Nuitka (compiles to C: faster and smaller, but long builds and a C compiler per platform); python-build-standalone plus the installed packages (no freezing problems, but bigger and many loose files).
